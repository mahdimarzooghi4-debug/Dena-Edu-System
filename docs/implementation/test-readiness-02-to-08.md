## تغییر آمادهٔ بررسی در این شاخه

چرخهٔ آزمون زمان‌دار برای آزمون‌های مؤسسه نیز اکنون در هر بار دیدن تلاش، ذخیرهٔ پاسخ و submit، عضویت فعال درس را داخل همان تراکنش قفل و دوباره بررسی می‌کند. آزمون PostgreSQL/HTTP لغو ثبت‌نام را پیش از این عملیات انجام می‌دهد و رد دسترسی برای هر سه مسیر را بررسی می‌کند.

مسیر آزمون دانش‌آموز در مرورگر نیز به‌صورت انتهابه‌انتها پوشش داده شد: شروع از کارت زمان‌بندی‌شده، ورود به تلاش، ذخیرهٔ پاسخ، ثبت نهایی و دیدن امتیاز. این تست از آزمون seed جداگانه استفاده می‌کند تا با تست‌های API هم‌زمانی و سقف تلاش تداخل نداشته باشد؛ همهٔ چهار job در run 38881668581 موفق شدند.

برای پرداخت، مرز `ServicePaymentGatewayAdapter` اضافه شده است: adapter آینده باید بایت خام webhook را امضا/ضد replay بررسی کند، سپس فقط رویداد `captured` با مبلغ ریال و سفارش معتبر را برگرداند. شناسهٔ رویداد با namespace درگاه به capture اتمیک دفتر مالی می‌رسد؛ خطای adapter یا payload نامعتبر بدون انتشار جزئیات رد می‌شود. تست واحد با adapter ساختگی مثبت/منفی را بررسی می‌کند. API درگاه یا قرارداد امضای vendor هنوز انتخاب/وصل نشده است.

برای multipart نیز `PrivateMultipartStorageAdapter` اضافه شده است: grant فقط از HTTPS origin allowlist صادر می‌شود، شکست grant session را abort می‌کند، complete فقط manifestی را می‌پذیرد که از فهرست واقعی storage خوانده شده، و کل شیء private پس از complete به‌صورت جریانی hash می‌شود. تست fake adapter مسیر موفق، origin/expiry نامعتبر، part ناقص و شیء نهایی نامعتبر را بررسی می‌کند. port هنوز به DB و routeها وصل نیست؛ هیچ URL امضاشده‌ای در برنامه صادر نمی‌شود و اتصال واقعی تا انتخاب storage API باز می‌ماند.

برای مصرف سهمیهٔ تماس، `ServiceCallUsageAdapter` بایت خام webhook را برای امضا و anti-replay می‌گیرد و فقط رویداد `ended` با دقیقهٔ نهاییِ ازپیش‌محاسبه‌شده را به ledger می‌رساند. ثبت مصرف، قفل سفارش→جلسه، وضعیت پرداخت/رضایت/پایان جلسه، ماندهٔ کافی، idempotency و یکتایی مصرف هر جلسه را enforce می‌کند. این boundary هیچ قانون زمان‌بندی/گردکردنی ندارد؛ adapter واقعی و endpoint تا انتخاب سرویس و تصویب قاعده خاموش می‌مانند.

در مسیر ثبت سفارش دانش‌آموز، قفل عضویت از `FOR SHARE` به `FOR UPDATE` تغییر کرد تا درخواست‌های هم‌زمان یک دانش‌آموز هنگام بررسی کلید idempotency پشت سر هم اجرا شوند. آزمون PostgreSQL انتهابه‌انتها، دو درخواست هم‌زمان با کلید یکسان، بازگشت همان سفارش، لغو تکرارپذیر پیش از پرداخت و باقی‌ماندن `paidAt` خالی را بررسی می‌کند.

برای ردیف ۳، migration دفتر سهمیهٔ زمانی و ثبت اتمیک سهمیه در capture اضافه شد. کلید یکتای رویداد از اعطای تکراری هنگام replay جلوگیری می‌کند و آزمون PostgreSQL مسیر رضایت، capture، replay، یکتایی سهمیه و نمایش مانده در دو پنل را پوشش می‌دهد. مرز ثبت مصرف نهایی جلسه نیز اکنون رویداد adapter-تأییدشده را برای جلسهٔ پایان‌یافته، با قفل ترتیب‌یافتهٔ سفارش و جلسه، کلید idempotency و سقف مانده در دفتر ثبت می‌کند؛ اما خودش زمان شروع/پایان را به دقیقه تبدیل نمی‌کند. قاعدهٔ محاسبه/گردکردن و انقضای سهمیه هنوز باید تصویب شود و مصرف خودکار تا اتصال provider فعال نیست.

برای ردیف ۴، چرخهٔ فرادادهٔ تماس به همان سفارش متصل شد: زمان‌بندی idempotent، شروع پس از زمان ثبت‌شده، پایان یا لغو کنترل‌شده، scope مؤسسه و ممیزی. سپس اتصال LiveKit آماده شد: endpoint توکن فقط برای تماس شروع‌شده، سفارش پرداخت‌شده، رضایت لازمِ ثبت‌شده، سهمیهٔ مثبت و عضویت فعال دانش‌آموز یا مؤسسهٔ مسئول پاسخ می‌دهد. توکن JWT با SDK رسمی LiveKit ساخته می‌شود، فقط به شناسهٔ همان اتاق مجوز می‌دهد و پس از یک ساعت منقضی می‌شود. این انقضا مدت تماس را محدود نمی‌کند؛ پایان تماسِ شروع‌شده اتاق را حذف و شرکت‌کنندگان را قطع می‌کند. رابط مرورگر تا تأیید آگاهانهٔ نمایش صوت/تصویر توسط کاربر، رسانه را فعال نمی‌کند؛ ضبط یا اشتراک صفحه در UI وجود ندارد. تنظیمات نمونه و preflight پرچم روشن‌سازی، URL امن و API key/secret را کنترل می‌کنند. اتصال برنامه به سرور self-hosted پیاده شده و runbook استقرار اضافه شده است؛ بااین‌حال VM، DNS/TLS/TURN و آزمون واقعی شبکهٔ Stage هنوز راه‌اندازی/اثبات نشده‌اند و webhook حضور/خروج نیز فعال نیست.

رابط مدیریت جلسه به صندوق مؤسسه اضافه شد. مؤسسه می‌تواند برای سفارش پرداخت‌شده و دارای ماندهٔ سهمیه زمان ثبت کند و جلسهٔ زمان‌بندی‌شده را شروع یا لغو کند، یا پایان جلسهٔ شروع‌شده را ثبت کند. آزمون PostgreSQL/مرورگر زمان‌بندی و لغو را از رابط طی می‌کند. رویدادها همچنان فقط فراداده‌اند؛ اتصال رسانه، صدور توکن و مصرف خودکار زمان فعال نیستند.

آزمون backup/restore در job عملیات CI پس از migration اجرا می‌شود. دو endpoint عملیاتی نیز اضافه شده‌اند: `/api/health/live` فقط در دسترس بودن process را اعلام می‌کند و `/api/health/ready` با `SELECT 1` دسترسی DB را می‌سنجد؛ پاسخ‌ها جزئیات خطا یا پیکربندی را افشا نمی‌کنند. آزمون PostgreSQL/Playwright هر دو را در role محدود بررسی می‌کند. API تجمیعی `/api/admin/media-operations` نیز فقط برای admin پاسخ می‌دهد و شمارش‌های صف را بدون upload ID، عنوان، hash یا خطای vendor برمی‌گرداند. سپس تمام shardهای DB نقش `dena_app_ci` را می‌سازند، سطح دسترسی آن را بررسی می‌کنند و build/آزمون‌های برنامه را با `DATABASE_URL` محدود اجرا می‌کنند؛ migrationها با حساب جداگانهٔ `dena_test` باقی می‌مانند. اسکریپت فقط URL دیتابیس loopback با نام کاربر و دیتابیس مخصوص CI را قبول می‌کند، یک schema و ردیف sentinel موقت ایجاد می‌کند، archive سفارشی می‌سازد، آن را در دیتابیس تازه restore می‌کند و مقدار sentinel را می‌خواند؛ دیتابیس و schema آزمایشی پاک می‌شوند. روش اجرایی و محدودیت‌های بازیابی محیط واقعی در [runbook PostgreSQL](../operations/postgres-backup-restore.md) ثبت شده است.

## شرط رفتن به مرحلهٔ تست محصول

برای آزمون محصول در Stage هنوز لازم است مالک محصول storage provider/API و تنظیمات واقعی آن را بدهد؛ LiveKit خودمیزبان با TLS و TURN در شبکهٔ Stage راه‌اندازی و اتصال دوطرفهٔ واقعی اثبات شود؛ متن/مدارک رضایت، قواعد مصرف و انقضا و سیاست نگهداری/دسترسی تصویب شوند؛ فریم‌های Figma برای مقایسهٔ بصری ارائه و پذیرش طراح ثبت شود؛ و محیط Stage با دادهٔ مصنوعی، پایش و runbook بازیابی آماده شود. اتصال upload چندبخشی به storage و صف پردازش تا مشخص‌شدن API/credential provider فعال نمی‌شود. بازبینی حقوقی/حریم خصوصی هم باید توسط مسئول مجاز انجام شود و از تست نرم‌افزار قابل جایگزینی نیست. تا انجام این گیت‌ها وضعیت «کد و CI آمادهٔ بازبینی» است؛ نه آمادگی Stage یا Production.
