# ثبت دانش‌آموز در پنل سازمان — نسخهٔ ۱

**وضعیت:** در شاخهٔ کاری پیاده‌سازی شده؛ migrationهای `0022` و `0023`؛ تست‌های واحد، lint، typecheck و build موفق‌اند. آزمون PostgreSQL واقعی و E2E این قابلیت اجرا نشده‌اند، چون `DATABASE_URL` در محیط حاضر تنظیم نیست. استقرار انجام نشده است.

## تصمیم‌های محصول

- سازمان می‌تواند دانش‌آموز را دستی، گروهی با CSV/XLSX یا از API ثبت کند.
- فرم مشخصات کامل می‌گیرد: نام، نام خانوادگی، کدملی، تاریخ تولد، جنسیت، موبایل و ایمیل اختیاری.
- با ثبت پرونده، حساب ورودی با موبایل ایجاد یا به حساب همان موبایل پیوند می‌خورد. OTP برای دانش‌آموز فرستاده نمی‌شود مگر آن‌که خودش فرایند ورود را شروع کند؛ حساب تا تأیید OTP موبایل تأییدنشده است.
- پرونده و دسترسی فقط در سازمان‌های تأییدشده‌ای دیده می‌شود که کاربر نشست در آن‌ها عضویت سازمانی فعال دارد. این کار به سازمان اجازهٔ دیدن یادداشت خصوصی، پاسخ آزمون، تلاش یادگیری، خرید، یا پروندهٔ سازمان دیگر را نمی‌دهد.
- پروندهٔ سازمانی تا زمانی که سازمان آن را صریحاً حذف کند نگهداری می‌شود؛ مهلت حذف خودکار ندارد. حذف تأییدشده فقط ردیف و PII مخصوص همان سازمان را حذف می‌کند؛ حساب مشترک دنا و عضویت دانش‌آموز باقی می‌مانند و مسیر حذف کامل حساب جداست.
- برای هر ثبت جدید، کاربر سازمان باید دریافت رضایت سرپرست قانونی را تأیید کند. زمان و شناسهٔ تأییدکننده در ردیف پرونده ذخیره می‌شود؛ این تأیید مسئولیت سازمان است و خود سامانه سند رضایت را جمع‌آوری یا اعتبارسنجی نمی‌کند. داده‌های قدیمی بدون رضایت ساختگی، بدون مقدار این فیلدها باقی می‌مانند.
- داشبورد ادمین موجود در کد، طرح قابل‌ویرایش خود را در صفحهٔ `07 — Admin Panel V1` فایل Figma دارد. صفحهٔ فهرست سازمان و نمونه‌های ثبت دستی، گروهی و API در `05 - Organization Panel V1` قرار دارند.

## مسیرها و قراردادها

| مسیر | کاربرد |
| --- | --- |
| `/organization/students` | فرم ثبت دستی، ورود CSV/XLSX، مدیریت کلید API و فهرست سازمانی |
| `GET /api/organization/students` | فهرست پرونده‌های تمام سازمان‌های مجاز به کاربر نشست |
| `POST /api/organization/students` | ساخت دستی؛ body شامل `organizationId`, `student`, و `guardianConsentConfirmed: true` است |
| `POST /api/organization/students/import` | فایل `file`، `organizationId` و `guardianConsentConfirmed=true` در `multipart/form-data` |
| `DELETE /api/organization/students/:studentId` | حذف پروندهٔ همان سازمان با body تأیید صریح |
| `GET/POST /api/organization/api-keys` | فهرست متادیتای کلیدها و ایجاد/چرخش کلید |
| `DELETE /api/organization/api-keys/:keyId` | لغو کلید در سازمان مجاز |
| `POST /api/v1/organization/students` | ساخت از API؛ محدوده از کلید Bearer استخراج می‌شود، نه body |

فیلدهای ساخت: `firstName`, `lastName`, `nationalCode`, `birthDate` به شکل ISO `YYYY-MM-DD`, `gender` از `female | male | prefer_not_to_say`, `phoneNumber` با قالب canonical ایران، و `email` اختیاری. کدملی ده‌رقمی با checksum اعتبارسنجی می‌شود. هر سه روش ثبت بدون تأیید صریح رضایت سرپرست رد می‌شوند.

نمونهٔ فراخوانی سازمانی:

```http
POST /api/v1/organization/students
Authorization: Bearer dena_org_…
Content-Type: application/json
```

```json
{
  "firstName": "…",
  "lastName": "…",
  "nationalCode": "1234567891",
  "birthDate": "2011-08-16",
  "gender": "female",
  "phoneNumber": "+989121234567",
  "email": "",
  "guardianConsentConfirmed": true
}
```

## فایل گروهی

- CSV با UTF-8 و XLSX پذیرفته می‌شود؛ حداکثر فایل ۵ MiB و ۵۰۰ ردیف دانش‌آموز.
- سرآیندهای لازم دقیقاً `firstName,lastName,nationalCode,birthDate,gender,phoneNumber` هستند؛ `email` اختیاری است. در XLSX تنها اولین worksheet و مقدار سلول‌ها خوانده می‌شود؛ فرمول‌ها رد می‌شوند.
- همهٔ ردیف‌ها ابتدا parse و اعتبارسنجی می‌شوند. اگر ساختار یا مقدار ردیفی نامعتبر باشد، پیش از نوشتن خطا بازگردانده می‌شود. تعارض با رکورد قبلی یا خطای هم‌زمان دیتابیس ممکن است باعث ثبت بخشی از ردیف‌های معتبر شود؛ پاسخ تعداد ثبت‌شده و شمارهٔ ردیف‌های خطادار را گزارش می‌کند.
- تأیید سرپرست در فرم بارگذاری برای همهٔ ردیف‌های فایل اعمال می‌شود و خود ستون فایل نیست.
- فایل در حافظه پردازش می‌شود و در فضای ذخیره‌سازی نوشته نمی‌شود. ZIP با سقف تعداد entry و سقف بازشدن فایل بررسی می‌شود.

## مرزهای امنیتی و حریم خصوصی

- دسترسی نشست بر اساس Better Auth و عضویت فعال از دیتابیس است؛ `organizationId` دستی در هر write با عضویت و هویت تأییدشده دوباره سنجیده می‌شود.
- API Bearer فقط به یک سازمان متصل است. کلید تصادفی ۲۵۶بیتی یک‌بار کامل نمایش داده می‌شود؛ فقط SHA-256 آن ذخیره می‌شود. چرخش کلید قدیمی را در همان تراکنش لغو می‌کند. هر کلید تا ۶۰ درخواست در دقیقه مجاز است.
- کدملی با AES-256-GCM و کلید مشتق‌شده از `BETTER_AUTH_SECRET` رمز می‌شود؛ HMAC جداگانه و وابسته به سازمان فقط برای تشخیص کدملی تکراری به کار می‌رود. صفحه فقط چهار رقم پایانی را نشان می‌دهد. کدملی کامل از API فهرست یا API سازمان بازگردانده نمی‌شود.
- موبایل از مدل مشترک کاربر Better Auth می‌آید؛ نام، تاریخ تولد، جنسیت، ایمیل و موبایل برای پنل همان سازمان قابل‌مشاهده‌اند. این فیلدها داخل DB برنامه رمزگذاری application-level نشده‌اند؛ رمزنگاری دیسک/شبکه و سیاست دسترسی دیتابیس عملیاتی باید جداگانه تأیید شوند.
- ممیزی فقط نوع عملیات و شناسهٔ پرونده/کلید را نگه می‌دارد، نه متن کدملی یا secret کلید.
- حذف پرونده از خود سازمان با تأیید صریح UI و body دقیق `DELETE_ORGANIZATION_STUDENT` انجام می‌شود. API فقط در صورت عضویت فعال همان سازمان پرونده را پیدا می‌کند و رویداد حذف را ممیزی می‌کند؛ حساب اصلی کاربر یا داده‌های آموزشی او پاک نمی‌شوند.
- سامانه زمان و تأییدکنندهٔ اظهار رضایت را نگه می‌دارد، اما مدرک رضایت را دریافت یا بررسی نمی‌کند. احراز اختیار سازمان برای گردآوری دادهٔ کودک و رویهٔ تصحیح اطلاعات هنوز تعریف نشده‌اند و پیش از استفادهٔ واقعی باید تعیین شوند.
